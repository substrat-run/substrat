# K-37 — Subject erasure splits by store: Tier 1 is redacted, platform-retained copies are…

**Subject erasure splits by store: Tier 1 is redacted, platform-retained copies are crypto-shredded, and the keys live in the directory** (#37; answers open question 17's spine half; implements master-plan §5.3's crypto-shredding sentence). `piiClass` had been enforced at the type level since the contracts package existed — an event carrying PII cannot be declared without a `subjectId`, on the stated grounds that "crypto-shredding must be able to key the erasure" — against a mechanism that did not exist anywhere in `packages/`. Building it surfaced the shape: **the mechanism divides the way the stores divide, not the way the data does.** Tier 1 is mutable, so erasing there is an ordinary redaction (`payload` nulled, envelope kept — §5.3's "pseudonymous keys and transaction facts remain"), and no cryptography is needed or wanted, because sealing a live payload would break the raw-SQL timeline projections CLAUDE.md explicitly blesses. A reap backup or stored dump is **immutable by design** (#493: "a backup that cannot restore is a false promise"), so a `DELETE` can never reach one — there, and only there, sealing each subject's payloads under their own key on the way out is what turns "erase from every copy we hold" into "destroy one key". **The key store's placement is the guarantee, not an implementation detail**: per-subject DEKs live in the DIRECTORY, wrapped by the host `SecretBox`, never in the scope database whose rows they protect — a key restored by the same dump that restores its ciphertext would silently reverse every erasure the restore rolled past (master-plan.md:316). **The tombstone is what makes it an erasure rather than a delay**: `shredSubject` keeps the key row with the key cleared, and the sealer refuses tombstoned subjects, because a key store that forgets who was erased erases them exactly once and the next backup undoes it. Order inside the action is fixed — redact the live spine FIRST, destroy the key LAST — since both halves are idempotent and converge on retry, so the tiebreak is which half-done state harms the person. Staff-triggered and absent from `BUILDER_ROUTES` (hosting-and-certification.md §3: "we provide extraction, they define scope"); audited in BOTH logs, the admin log because it mutates and the access log because it destroys evidence. Implemented in both adapters with the crypto factored into the kernel (`createSubjectKeys`), so an adapter supplies three row operations and no cipher

## Why

The constraint that decided the design is one line of code: **`ctx.emit` is synchronous and Web Crypto is not.** Sealing at emit would have meant an async `emit` — a breaking change to every operation ever written, against D-28's additive-only rule — so "encrypt PII at write time" was never actually available, and discovering that early is what redirected the work to the egress path where the un-deletable copies actually are. The second finding reframed the issue: **there is no Tier-2 event drain** (`_substrat_outbox.drained_at` is still dead; K-24 built the sink for the access log only), so §5.3's "GDPR in an immutable lake" is a promise about a lake that does not exist. Building the mechanism for the lake would have been building against an absent store; building it for the backups shipped in #542/#543/#545 puts it where the exposure is today and leaves the lake inheriting it for free. Five limits ship documented (§13.1) rather than discovered — one subject per event, vertical-owned tables untouched, copies already handed out, the PITR window, and a directory restore resurrecting a key — because the failure mode this issue warned about is not a missing mechanism but an oversold one: "That's a real Article 17 scenario. Don't promise it"
