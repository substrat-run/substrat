# K-33 — Verticals serve IN PLACE from one stable script; per-version scripts become the push archive

**Verticals serve IN PLACE from one stable script; per-version scripts become the push archive** (#286; supersedes orchestration.md §5.3's one-script-per-version *for serving*). A Durable Object namespace belongs to its script, so under per-version serving a version update rebound scopes to **empty storage** — data never followed, the kernel's append-only `SqlMigration[]` never met production data, and every live-tenant deploy was a manual backup→update→restore ritual with post-restore repairs. Now: push still uploads an archive script per version (`<slug>-<versionId>` — admission review + the bundle store), but a prod promote re-uploads the promoted bundle onto `stableDeploymentRefFor(slug)` where every scope's DOs live. In-place uploads keep secrets (`keep_bindings` — deletes the re-put-per-script ritual) and send only the DO-class delta under a bumped tag, diffed against directory-recorded serving state (`verticals.serving_*`), never against queried Cloudflare state. Routing is per-scope truth: `scopes.serving_ref` (born-on at provision; **adopt-serving** = export → restore → flip for legacy scopes, data-first so a crash leaves the old script serving intact). The safety net: publish badges **code-only vs schema-change** (migration-digest diff vs predecessor — the same signal promote's acknowledgement reads); the scope DO takes a **PITR bookmark** immediately before an upgrade's migration pass (`_substrat_migration_bookmarks`, skipped on first provision, tolerated absent where PITR doesn't exist); and an audited, time-boxed **rewind** (`rewindScope`, 24h window unless forced) restores schema AND data to that instant. Conceded knowingly: per-scope staged rollout across versions — illusory for stateful scopes under either model — so blast radius stays per-vertical (D-30's boundary)

## Why

The correction worth recording is that §5.3 priced the scripts as stateless when the scope DO *is* the app: the pinning/rollback benefits it bought could not coexist with data, so the design was paying a fatal cost (stranded data) for goods it never received. The tell was that the migration machinery — append-only, expand-contract, per-scope frontier, the whole §5.3 reconciliation apparatus — was dead code in production, replaced by a runbook; when the mechanism a design is built around never executes, the deploy model is contradicting the data model. DO transfer-between-scripts (verified supported, same dispatch-namespace context) was considered and rejected: all-or-nothing per class, one pending transfer at a time, and it still buys no per-scope staging — the audit value of immutable script names lives in the version registry instead. The rewind's honest caveat is enforced where it can't be skipped (the DO refuses stale bookmarks, not the UI): PITR restores the ENTIRE database, so backout is a first-hours tool and #278's backup/restore is the considered path — a rewind that silently discarded a day's writes would be a worse failure than the one it repairs. Failure ordering is chosen so every partial state is visible and retryable: channel moves before serve (a failed serve leaves `servingVersionId` trailing prod — promote again retries), data lands before routing flips (adopt), and the audit entry precedes the destructive rewind
