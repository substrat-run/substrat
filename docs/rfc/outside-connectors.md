# RFC: connectors that live outside this repo

**Status: proposed.** This is a design for [#2614](https://github.com/substrat-run/substrat/issues/2614), not an implemented upload or execution path. The questions in §6 need a maintainer decision before the contracts or runtime change.

## 1. Boundary and release

Today the control plane imports each connector package and compiles its `ConnectorRegistration` into [`CONNECTORS`](../../apps/control-plane/src/connectors.ts). That one array supplies inspection, binding, sweep, dispatch, callbacks, consent, mail and grants. The control plane holds sealed connection credentials and outbound network access. An outside package therefore cannot run merely because it is published: adding it to `CONNECTORS` requires a dependency, a code change and a control-plane deploy. The dashboard's provider catalog and `connectionBindingOptions` also name providers in source. This RFC proposes one generic outside-connector path, with no per-provider package dependency or release pin in this repo.

An **outside connector release** is an uploaded, self-contained worker bundle, not a package name resolved at request time. Its archive contains the JavaScript entry and its bundled runtime dependencies, plus a manifest naming the provider slug, package name and version, connector API major version, required runtime features, declared roles, standing grants, binding-option schema, credential input fields and permitted outbound origins. It names the file-source contract version if it emits `fileSourceChange` or reads `fileSourceWriteRequest`. The platform validates the archive and computes SHA-256 over the exact stored bytes on upload; `(provider, digest)` identifies the release. The uploader records the package version and source references for review, but neither an npm version nor a repository commit substitutes for the digest. The platform does not rebuild from source or fetch a package when serving a connection.

The outside package compiles against versioned interfaces published from this repo. Its bundle targets a **connector worker protocol** adapting the present `ConnectionInspector`, `ConnectionBinder`, `ConnectorSweeper` and `ConnectorHandler` roles. The adapter preserves their observable results and the existing file-source schemas, but does not serialize `ScopeHost`, `HostAdmin` or a live `ConnectorContext` into the worker. A major protocol mismatch refuses upload or activation; additive minor fields are ignored only where the protocol says they may be. The release declares its role set and the platform rejects an undeclared call. Callback, browser consent and mail roles need separate protocol definitions and are outside the first slice. A provider slug already owned by a compiled connector cannot be claimed by an outside release.

## 2. Upload and approval

Upload stores an inert release row and its bytes. The row records uploader, time, provider, platform-computed digest and the submitted manifest. Upload alone never makes the release selectable. A separate staff action approves `(provider, digest)` after reviewing the exact archive. Its append-only record carries approver, time, reason, structured source references `(repository, commit)`, the accepted manifest facts and an **isolation review**: allowed network egress, how credential access stays behind the control-plane relay, and memory, CPU, request, byte and concurrency limits. The review records evidence and whether each condition is met. A condition recorded as unmet is visible; whether it blocks approval is Q3. No service upload token approves a release. The admin log also records approval and revocation, while the approval row keeps its own actor and time.

The manifest facts are fixed on first approval for that digest. A later approval after revocation must agree with them; changed bytes receive a new digest. Approval is live until revoked, with at most one live approval per `(provider, digest)`. The control plane checks the live approval on every selection and invocation, with no approval cache. An unavailable approval read fails closed with 503. A digest proves which bytes were stored, not that the stated source produced them or that the isolation review's claims hold. This follows the [store-driver release approval RFC](./store-driver-release-approval.md)'s division between upload, human approval and runtime checks, without copying its compiled driver-id requirement: a connector provider id has no equivalent backup or erasure gate in the released CLI.

## 3. Connection selection and lifecycle

The approved manifest becomes the provider's data-backed catalog entry. The same generic path supplies credential fields, declared grants and a validated binding-option schema to the existing connection and binding doors; it does not add a switch arm or dashboard form per provider. Existing tenant authorization and the connection relay still decide who may create a connection. A new connection chooses a provider and an approved digest. For a simpler UI the staff-set **current release** for that provider may supply the initial digest, but the chosen digest is stored with the connection. Its bindings and deliveries use that release until explicitly moved. Compiled connectors retain today's provider-only behavior.

An upgrade approves a new digest first, checks protocol compatibility and the provider's binding schema, then moves selected connections under a per-connection hold. The platform stamps the selected digest on each queued delivery, so retries keep it and the old release remains available until they settle. A rollback is the same move to a still-approved earlier digest; it never means fetching the earlier npm package again. A changed file-source mapping may need a migration plan before a move: `itemId`, cursor and binding-option meanings must remain usable, or the move is refused pending an explicit reset/rebind decision. Idempotence remains the connector's obligation under [connections §6.3](../architecture/connections.md#63-file-bearing-sources-the-reference-shape).

Normal revocation refuses while any live connection selects the digest or an assigned delivery still needs it. A guarded walk of connection and delivery records, under the same hold that moves assignments, establishes that condition before recording a revoke. An emergency revoke requires a staff reason and stops new starts immediately, including rollback to that release; work already executing may finish. A connection left on that digest reports unavailable until moved. Approval read failure also stops new work with 503, including a retry; it is never treated as an empty catalog. Release bytes and approval history remain for audit after revocation. Removing bytes requires the same no-reference guard and is a separate retention decision.

## 4. Execution boundary

**Recommended:** upload each approved release as a separate worker script, addressed by digest. The control plane alone chooses the connection and release, verifies approval, and invokes that worker. It does not give the worker the control-plane environment, directory binding or a general connection-store client. A narrow relay mediates the operations the selected role needs: the selected connection's credential use, permitted provider egress, binding reads and writes, landing calls and per-delivery attachment access. The relay derives tenant, vertical, scope, provider and connection from the control plane's selected record and delivery; the worker does not choose a different connection by supplying identifiers. The control plane validates relay requests and returned file-source shapes, accounts for byte and call limits, and owns the audit trail. Resource ceilings and egress policy must be enforced by the deployment and relay, not merely listed in the manifest.

This is a proposed boundary, **not a present isolation guarantee**. The existing connector interfaces pass broad host objects, and the current Workers-for-Platforms namespace is used for vertical scripts. A separate connector namespace, relay protocol and evidence that its bindings, outbound traffic, CPU and memory limits enforce the reviewed policy are prerequisites to claiming isolation. The first release must not be enabled until those checks exist. Review of an uploaded release remains necessary even then; the review records what was checked and what remains unproved.

The cheaper operational alternative is to run the approved bundle in the control plane's isolate. It can reuse the present connector objects and avoid a worker relay, under the same digest and approval record. It gives outside code the control plane's ambient reach, however, so approval of the bytes is the only meaningful boundary. Dynamic loading of uploaded modules in that isolate is also unestablished on the current runtime; bundling them into the deploy would restore the per-release deploy this RFC aims to remove. Q1 asks the maintainer to choose the execution boundary explicitly.

## 5. Verification and first slice

CI should validate the archive and manifest schema, protocol-major compatibility, provider collision rule, role and grant declarations, and the generated bundle's import closure. A fixture outside package should pass contract cases for probe, bind, sweep and dispatch through the **same worker relay** used in production, including refusal of an unapproved or revoked digest, a failed approval read, an incompatible release and a bounded request. File-bearing fixtures check the four §6.3 invariants: no data outside the bound folder, explicit write conflict, at-least-once `itemId` handling and deletes only on an answer about that item. CI can establish protocol behavior and configuration; it cannot prove a provider's live API behavior, source provenance or runtime isolation by itself. Those belong in release review and a controlled live check.

The first slice is **one outside file-bearing connector end to end**: upload its published package as a bundle, compute and display the digest, approve it as staff, select it on one connection, run probe/bind/sweep/dispatch in a separate worker via the relay, then exercise upgrade, rollback and guarded revoke. It uses the existing credential relay and file-source schemas. No marketplace, self-service publication, broad provider migration or multi-tenant publishing flow is needed for that slice.

## 6. Questions for the maintainer

1. **Execution boundary?** Recommend a separate worker and narrow relay (§4). The in-isolate route is smaller, but its isolation claim is limited to review of the exact bytes and dynamic loading is unproved.
2. **How is a connection pinned?** Recommend an approved digest stored on the connection, with a staff-set current digest only as the default for new connections. This makes upgrades and rollback explicit and keeps retries on the selected release.
3. **Can approval record an unmet isolation condition?** Recommend recording it but refusing activation until the required egress, credential and resource controls are demonstrated. This makes the status honest without treating review prose as enforcement.
4. **Who may approve?** Recommend a staff sign-in, recording uploader and approver without a two-person rule in the first slice, as the store-driver RFC decided. A later two-person rule can use those records.
5. **What does emergency revoke do?** Recommend a reasoned staff override of the reference guard that stops new invocations, while reporting selected connections as unavailable until moved. It cannot cancel work already running.
6. **How much of `ConnectorRegistration` is in v1?** Recommend probe, bind, sweep and dispatch with declarative grants and options. Define callback, consent and mail worker protocols when an outside connector needs them.
