# RFC: audit rows for HostAdmin writes across scope storage and the directory

**Status: proposed.** This is a recommendation for [#2527](https://github.com/substrat-run/substrat/issues/2527), not a change to the HostAdmin contract or an implementation decision. The directory transaction rule in [control-plane.md](../architecture/control-plane.md) §4.4 covers writes whose state is in the directory. A scope tuple, capability, event stamp or restored database is elsewhere: a per-scope SQLite file in adapter-sqlite, or a ScopeDO in adapter-cloudflare. Neither adapter can commit that store and its directory admin log in one transaction.

## What the code does today

The table names the actual order. “Scope first” means a committed effect can lack its admin row when the later directory insert fails. “Directory first” means a row can remain when the later scope step fails. A returned error does not imply that the earlier step rolled back.

| Family | adapter-sqlite | adapter-cloudflare | Retry and remaining gap |

It does not recover the missing row of the first attempt. Tenant-node variants commit with the directory row and are outside this RFC. |

These orders follow the adapter implementations (`packages/adapter-sqlite/src/index.ts`, `packages/adapter-cloudflare/src/host.ts`) and the existing two-phase helper. [K-4](../decisions/K-004-event-emission-transactional-via-outbox-in-scope-storage.md) already puts *domain* event emission in a scope-local outbox; that outbox does not currently carry HostAdmin admin rows.

## Choices

### 1. Directory intent and outcome

Before calling the scope, append an intent row with one operation key, action, actor, target, and the parameters needed to interpret the request. After the scope answers, append an `applied`, `refused`, or `failed` outcome under that key. Reuse the kill-switch and import-cursor convention: an outcome insert failure is logged and returned as an audit warning where the method can return a value; `settleUnrecordedOutcome` later closes an open intent as `unknown`. The scope action must not be reported as rolled back merely because its outcome row failed.

This needs no new scope table or migration. The admin log's existing structured `after` field can carry phases and correlation, although readers must group rows and distinguish **intent** from **confirmed effect**. It adds at least two directory writes and two cross-store hops to each audited mutation. An intent insert failure stops the scope write. A failure after intent but before scope execution leaves an open intent; a failure after scope commit but before outcome leaves the *same visible shape*. Settling to `unknown` preserves evidence that a request occurred, but does not prove whether it took effect. A read of scope state may sometimes clarify current state, not the exact historical outcome after later writes. Retrying the operation must not manufacture a second “applied” claim for an earlier attempt.

On SQLite, the scope actor turn and directory calls are separate even in one process. On Cloudflare, the ScopeDO can be in a different deployment and reached through delegation, making a lost response another ambiguous case. Both need the same operation-key and phase semantics in the shared contract; Cloudflare also needs to avoid treating a transport error as proof of no effect.

### 2. Scope-local admin outbox, drained into the directory

Write a pending admin envelope in the *same scope transaction* as the tuple, capability or event stamp. A drainer copies it to the directory using a unique delivery key, then marks it delivered in scope storage. If copying succeeds and acknowledgement fails, a repeat delivery must be deduplicated at the directory. The stored envelope must contain the platform actor and attribution, target, action, before/after facts and the scope commit time; a later directory read cannot reconstruct all of those facts. Directory queries will lag the scope commit until a drain succeeds, and deletion must retain or flush the pending envelopes before storage is destroyed.

This gives the strongest eventual link between scope effect and audit row for a *single transaction*, but requires a persisted table and migration in both per-scope SQLite files and ScopeDO storage, a drain protocol, retention and backfill rules, and deployment compatibility across separately shipped hosted scopes. A coordinator that cannot reach a delegated ScopeDO cannot drain it. A scope wipe, PITR rewind, dump import, or key-destruction flow can remove or replay pending envelopes; each needs its own ordering and deduplication rule. Multi-pass reconcile, import, and restore still need a higher-level receipt for partial progress. Directory-first connection grant records do not fit a scope-originated outbox without changing which event the existing row describes.

### 3. One-sided order plus idempotent re-record on read

Keep the scope-first writes and have an admin read or retry compare current scope state with directory rows, inserting a missing row. This avoids a new scope table and the extra pre-write directory call. It is useful for repairing a known durable projection, as the connection-grant record already does for hosted tuple delivery.

It is not sufficient as the general admin-log rule. The read does not know the original actor, reason, timestamp or before-state unless these are persisted elsewhere. Revokes and drain marks deliberately return no change on retry; a later grant or restore can overwrite the state being examined. A repair row would describe the **read-time** state, not reliably the original action. Making reconciliation exact requires a durable operation receipt at the scope, which becomes the outbox in choice 2. A failed directory insert can also recur on every read; the gap has no bounded closure.

## Recommendation and sequence

Adopt **directory intent and outcome** as the first shared rule for scope-node permission writes. Begin with `assignRole`, `unassignRole`, `grant`, `grantToOrg`, `grantToSystem`, `grantEntityShape`, and `mintCapability`, on both adapters and through delegated hosted scopes. Give each call one correlation key; write intent before any scope mutation; record the scope's returned result as outcome; settle an unrecorded outcome to `unknown`. Preserve the present no-op rules in the outcome so “already revoked” is not reported as a new revoke. The fault cases should establish separately: intent failure makes no scope change; scope failure leaves a failed or unknown intent; outcome failure leaves a committed scope change with a discoverable intent. This is the smallest path that removes the *silent* scope-first audit gap for the high-value permission family without changing persisted scope shape.

Handle `reconcileEntityGrantShapes` in a subsequent pass with an intent per bounded pass or another explicit partial-progress receipt; one whole-call outcome cannot accurately describe an early committed pass followed by failure. Keep `grantToConnection`'s directory record plus audit row and its delivery repair path; address SQLite's missing reconcile separately before claiming delivery convergence. Keep `revokeCapability`'s existing two-phase helper, and keep kill switches and `moveImportCursor` on their established pattern. Their shared grammar should guide the new cases rather than be replaced.

Leave lifecycle, drain and switch reassert methods for method-specific follow-ups. Provision, import, restore, deletion, rewind and erasure include directory state, scope storage and sometimes external stores; a generic two-row wrapper cannot truthfully summarize their intermediate commits. `markEventsDrained` needs a durable batch receipt if the exact egress count must survive an audit failure. `redrainEvents` and `rewindScope` already record intent first, but need an explicit outcome/settlement contract if they are to promise confirmed results. Reassert has a directory switch record and fence for convergence, while its individual move receipts still need a fault case. Each follow-up should name the effect boundary and its retry rule before changing the log.

If confirmed outcome, rather than a discoverable request with a possible `unknown`, becomes the requirement for all single-scope writes, take choice 2 through a separate decision and migration plan. This RFC does not claim that intent/outcome makes two stores atomic. It gives the directory a durable record before the scope is asked to change and makes uncertainty visible.
