# RFC: builder model catalog & harness efficiency

**Status:** proposed — tracks a research pass over opencode/models.dev (2026-08-15) and turns it
into a ranked adoption plan. · **Depends on:** [builder-studio.md](./builder-studio.md) (§5.3 the
provider seam, §5.4 prompt caching — this doc is the concrete follow-through on both),
[engine-metering.md](./engine-metering.md) (quantities vs pricing; the studio's rate card is
vertical vocabulary). · **Touches:** `apps/builder` (pricing, picker, providers),
`packages/builder-generator` (the turn loop, the tools).

**What this is:** the inventory of what our turn loop already does to keep LLM calls cheap and
reliable, what opencode does that we don't, and which of those gaps we intend to close — each with
the *why*, so a checked-off row is a decision executed rather than a feature drifted into.

**Sources:** full reads of `sst/opencode` (branch `dev`) and the live `models.dev` catalog, then
targeted passes over `Aider-AI/aider` (edit formats, repo map), `BerriAI/litellm` (the pricing
catalog), and OpenHands classic 0.62.0 + `OpenHands/software-agent-sdk` (condensers) — all
2026-08-15. Licenses: opencode, models.dev, LiteLLM, OpenHands are MIT; aider is Apache-2.0.
All permit code lift and data consumption for the private builder; a lift carries the upstream
copyright notice (and, for aider, the Apache-2.0 text + a changes statement).

---

## 1. The frame

Two forces make this worth a document now:

1. **We started billing.** The pricing work (PR #661) charges builders per token at list + 20%.
   The moment usage is billed, the harness's token efficiency is not an optimisation — it is the
   product's margin and the builder's bill, and the rate card's correctness is a billing-integrity
   question.
2. **We hand-maintain what the ecosystem already maintains.** The rate card
   (`apps/builder/src/pricing.ts`), the model pairs (`apps/builder/src/model-pairs.ts`), and the
   picker catalog all carry hand-verified model ids, prices, and capabilities — each with a
   comment admitting it goes stale ("update them here when the catalog moves"). models.dev is a
   community-maintained, schema-checked catalog of exactly these facts for ~185 providers /
   ~6,500 models.

opencode is the strongest open reference for both problems: it is a production agent harness whose
entire model story sits on models.dev, and its session loop encodes several years of accumulated
cost tricks. The research confirmed our loop independently arrived at several of them (§3.1) —
which is validation, not wasted work — and found four genuine gaps (§4), plus one defect of our
own the comparison made visible (H5: the tier-1 gates' verdict never reaches the model).

**Non-goals, stated first:** we are not adopting opencode's provider layer (its 66 KB
`transform.ts` exists because it supports 185 providers; our seven-provider table in
`providers.ts` does not have that problem), not building favourites/recents picker chrome for an
internal PoC, and not introducing runtime dependence on a third-party endpoint for billing data
(§2.2).

## 2. The catalog: models.dev

### 2.1 What it is

`https://models.dev/api.json` — per provider: env-var names, base URL, AI SDK npm package. Per
model: `cost` (input/output/cache_read/cache_write per 1M tokens, context-size tiers), `limit`
(context/output), capability flags (`tool_call`, `reasoning`, `structured_output`), `family`,
`release_date`, `status: deprecated`. The data is PR-reviewed TOML in `sst/models.dev`, MIT.
opencode consumes it via a mirror + disk cache + compile-time snapshot, never blocking on the
network.

### 2.2 Decision: vendored snapshot from TWO sources, not runtime fetch

The rate card's source of truth becomes a **checked-in snapshot** generated by a script
(`tools/` or `apps/builder/scripts/`) from two community catalogs, filtered to the
providers/models we actually serve. Runtime fetching — opencode's model — is right for a tool
that only *displays* cost; it is wrong for one that *bills* on it:

- Community catalogs are advisory grade. A bad PR upstream must not silently change what we
  charge.
- A checked-in snapshot makes every price change a **reviewable diff** — the same shape as the
  permission-diff checkpoint: CI can re-emit and `--check`, a human reads the diff, drift cannot
  merge invisibly.
- The snapshot regenerator still deserves a one-time manual check against the provider's own
  price page for models we bill.

**Why two sources.** The LiteLLM pass (its root
`model_prices_and_context_window.json`, MIT, schema-CI'd, updated multiple times daily — the
DashScope entries four days old at time of research) showed the two catalogs are not
interchangeable, and the disagreement is exactly where billing goes wrong:

- **DashScope prices qwen by context tier, and models.dev only carries tier 1.** LiteLLM's
  `dashscope/qwen3-max` entry is a three-tier table rising to ~2.5× the base rate above 128k
  input tokens; models.dev (and our current flat rate card) has the tier-1 price only. Billing
  long-context qwen turns from either would **undercharge up to ~2.5×**. DashScope tiering is
  all-or-nothing (the whole request bills at the tier its total input lands in), which is the
  semantics the rate card must implement.
- LiteLLM also carries Anthropic's **above-200k long-context rates** and the **1-hour cache-write
  rate**, per-tier cache-read rates, `deprecation_date`, and `source` URLs (audit trail to the
  provider's price page); models.dev has a single flat `cache_write`.
- models.dev's strengths remain: sane units (USD per 1M as plain decimals — LiteLLM is per-token
  floats in scientific notation, so its values need careful float→decimal conversion), per-model
  `release_date`/`last_updated` (a staleness signal LiteLLM only has via git history), `family`,
  and `open_weights`.

So: **models.dev is the primary card** (units, metadata, families); **LiteLLM is the authority on
pricing *structure*** (tiers, cache TTL split, long-context thresholds) and the cross-check. The
generator diffs the two and fails on disagreement in any billed dimension — and the diff must
cover the tiered/cache dimensions, not just base input/output rates, because base rates are where
the sources agree and tiers are where they don't. LiteLLM's cost-calculator regression tests
(e.g. their DashScope tier tests) are portable fixtures for our own pricing tests. One known
editorial divergence to encode, not "fix": models.dev reports the 1M-beta context for
long-context Anthropic models where LiteLLM reports the standard 200k tier — they answer
different questions.

What the snapshot replaces/feeds:

| Consumer | Today | With snapshot |
|---|---|---|
| Rate card (`pricing.ts`) | 2 hand-entered Qwen rows, input/output only, flat | all served models, incl. `cache_read`/`cache_write` rates and DashScope context tiers |
| Picker catalog (`hostedProviderCatalog`) | hand-listed | generated, `status: deprecated` filtered |
| Cloudflare model list (`listModels`) | account API, task-filtered only | cross-referenced with `tool_call: true` — stop offering models that cannot run a build turn |
| Context limits | none (overflow = raw provider error) | `limit.context` per model, feeds §4.3 |

**Two concrete billing bugs this fixes.** (1) *Cache pricing:* the turn loop already reports
`cachedInputTokens`/`cacheWriteTokens` (they are in the usage event), but the rate card has no
cache rates — so cache traffic is either billed at the full input rate or not at all, both wrong.
Anthropic cache writes are 1.25× input and reads 0.1×; at our volumes with the moving-breakpoint
strategy (§3.1) most input tokens *are* cache reads. (2) *Context tiers:* the flat qwen rates
undercharge long-context turns up to ~2.5× (see above) — and long-context turns are precisely
what a 40-step build produces. The snapshot carries both dimensions; the pricing code grows tier
selection (all-or-nothing by total input, DashScope semantics) and two cache fields.

### 2.3 Later: pairs by family, enablement in the picker

- **`family`-based pair selection.** opencode picks its small model by models.dev `family` +
  newest `release_date`. Our `MODEL_PAIRS` hardcodes ids and goes stale on every catalog bump.
  Once the snapshot exists, a pair can be declared as *families* (`qwen-flash` / `qwen-max`) and
  resolved to the newest non-deprecated member. Deliberately after the snapshot lands, not with
  it — id-level control is fine while the model list is two entries long.
- **Credential-gated picker.** opencode only enables a provider whose credential exists. We
  already know `envVar` per provider; the picker should grey out providers whose secret is not
  configured instead of letting the turn fail with an auth error.

## 3. The harness: where we stand

### 3.1 Already at parity (or ahead) — no action

Recorded so nobody "adopts" these twice:

- **Cache-stable prefix discipline** (builder-studio §5.4, implemented in
  `packages/builder-generator/src/ai-sdk.ts`): stable system + skills prefix with Anthropic
  breakpoints, volatile workspace brief riding in the final user message. opencode does the same
  (one joined system message, alphabetically sorted tools, dynamic content as user parts).
- **Moving per-step breakpoint** (`withMovingBreakpoint`): equivalent to opencode's
  last-2-messages marking. Without it the tool loop re-bills the whole transcript per step.
- **Stale-payload pruning** (`pruneStalePayloads`) for non-Anthropic dialects — we are *ahead*
  here: opencode's prune is opt-in and threshold-based; ours supersedes-by-target per step.
- **Tool output caps**: read head+tail 24 KB; command output tail-biased with an asymmetric cap
  (1.5 KB on success, 8 KB on failure) — opencode caps too but has no success/failure asymmetry.
- **Phase-based model routing** (`model-pairs.ts` fast/strong): opencode has *no* cost-based
  routing (small model does titles only). Confirmed our design is not missing a subtler trick.
- **History hygiene**: opencode keeps history append-only with no read-dedup — so there is no
  cleverer mechanism we overlooked; pruning + caps + compaction is the whole known toolbox.

### 3.2 Gap analysis — what opencode has that we lack

Ranked by expected effect on the bill and on turn survival:

**H1 — an `edit` tool (string replacement).** Our only mutation is `write_file` with complete
content: a 3-line change to a 300-line file re-emits the file at output-token prices — the
expensive tokens, on the strong model. This is the single biggest cost lever available to us, and
it *shrinks* the payloads that `pruneStalePayloads` exists to clean up. The aider pass settles
the two design questions:

- **Apply strictly, reflect on failure — no fuzzy apply.** opencode ships fuzzy replacers; aider
  deliberately disabled theirs (dead code behind a bare `return`). Aider's ladder is: exact
  match → uniform-leading-whitespace-normalised match → `...`-elision blocks — and anything else
  becomes a *structured reflection* to the model: the failed block, a "did you mean these actual
  lines?" excerpt (best similarity window over the file), an "already applied?" hint when the
  REPLACE text is present, and explicit partial-apply accounting ("the other N blocks were
  applied — don't re-send them"), capped at 3 reflections. Guessing at a fuzzy match risks silent
  wrong edits in a loop whose oracle (the gates) runs only at turn end — aider's shape is the one
  to port. Their matcher + reflection message is self-contained in `editblock_coder.py`
  (Apache-2.0; header note + license text on the port).
- **Format is per-model, and the weak-model risk is measured.** Aider assigns edit format per
  model (a 357-entry table): search/replace for capable models, whole-file for weak ones. Their
  polyglot leaderboard quantifies why — frontier models emit well-formed search/replace blocks
  ~97–99% of the time, sub-tier models collapse (QwQ-32B: 68%). So H1 ships as
  **format-per-model**: the strong tier gets `edit_file`, `write_file` stays (for new files, and
  as the declared format for models that can't hold search/replace), and the pair table
  (`model-pairs.ts`) is where the format flag lives. Evals then measure, per model, what aider's
  leaderboard measures globally.

**H2 — retry with `retry-after` honouring.** Our loop turns any provider error into a fatal
event: one Anthropic 529 mid-turn kills a 30-step build and its cache investment. opencode
retries 5× (2 s base, ×2, 25% jitter), honours `retry-after`/`retry-after-ms` headers, classifies
retryables (5xx, 429, "overloaded", ECONNRESET…), and **never** retries context overflow. The AI
SDK's `maxRetries` covers part of this; the classification and header-honouring are worth porting
from `session/retry.ts`.

**H3 — overflow handling, then compaction.** A 40-step build turn can exceed a smaller model's
context; today that surfaces as a raw provider error and a dead turn. Our cross-turn history is
already text-only (`GeneratorTurn[]`) so the pressure is in-turn; the snapshot's `limit.context`
(§2.2) is the input any trigger needs. Both opencode and OpenHands were read here; OpenHands is
the stronger reference — they treated condensation as a research problem and published the
numbers:

- **The evidence:** on SWE-bench Verified, condensation held resolve rate flat (54% vs 53% on
  the subset run; 200 vs 203 on the full run — a wash) while per-turn API cost settled to **less
  than half** of baseline and response latency stayed flat instead of growing with iteration
  count. Their honest caveat transfers directly to us: compaction **invalidates the cached
  prefix**, so on cache-friendly providers (our Anthropic path, §3.1) one full run actually cost
  *more* with condensation — the win is real on long runs and on providers without placeable
  cache, and it must be measured, not assumed. Compact reluctantly on Anthropic; more eagerly on
  the OpenAI-compatible side.
- **The design worth porting:** (1) *one code path for both triggers* — a proactive check
  (tokens ≥ limit − reserve, opencode reserves 20k) and the reactive catch of a provider
  overflow error both funnel into the same condense-then-retry step, never two mechanisms.
  (2) *Compaction is an event, not a mutation* — OpenHands appends a condensation event and
  applies it when building the model view, so raw history survives for the UI and replay; that
  fits our event-sourced turn loop (`BuildEvent`s) naturally. (3) *Pin head, summarize middle,
  keep tail* — system + first user message stay verbatim (`keep_first`), recent tail stays
  verbatim, only the middle is summarized; cuts must respect tool_call/tool_result pairing or
  the provider rejects the replay. (4) *A structured summary prompt*, not freeform — both
  projects converged on labeled sections (objective / completed / pending / code state / failing
  tests / files touched) with "preserve exact file paths, symbols, commands, error strings";
  either template is liftable (MIT). (5) *An escalation ladder* — normal condense → reject if it
  frees too little (&lt;10%) → hard reset (summarize everything with shrinking per-event caps) →
  error; plus a death-spiral guard (consecutive condensations with no progress between them).

**H4 — cache plumbing + sampling defaults for the OpenAI-compatible side.** Two one-liners:
`promptCacheKey`/`prompt_cache_key` = a stable per-project id on OpenAI-family requests (routes a
session's requests to one cache shard); and per-family temperature defaults — opencode sends
**0.55 for qwen** (0.6–1.0 for kimi/glm), where we send nothing on our *default provider*. The
temperature row is a quality lever, not a cost one, but it lives in the same providerOptions plumb.

**H5 — red gates never reach the model (our own defect, surfaced by the comparison).** The
tier-1 gates run after every turn (builder-studio §9.1), but their verdict died at the UI and the
commit trailer: durable history carried only user + assistant text, and `workspaceBrief` is
`git log --oneline`, which drops the `gates: red` trailer. The model could leave the tree red and
open the next turn believing everything was fine — an oracle nobody reads is not an oracle. The
fix is two-part, and the *audience* is why the studio handles it rather than the builder: a
non-technical builder can do nothing with a raw typecheck error.

1. **Feed-forward:** a red run's report (`gateReport` in `gates.ts` — failed gates with trimmed
   output tails) persists in project state and rides into the next turn's volatile context,
   beside the workspace brief. Deleted the moment the tree goes green.
2. **Capped in-turn repair loop:** after a red run, the host re-invokes the generator with a
   structured repair prompt (`gateRepairPrompt`) and re-runs the gates — aider's
   reflection-with-a-cap shape at turn scale. `MAX_GATE_REPAIRS = 2`; every attempt is a full
   billable model run, so the cap is a billing control as much as a safety one. The loop stops
   early when an attempt changes no files (no progress), and never triggers on a chat-only turn
   over a pre-existing red tree.

Carve-outs, both load-bearing: **`blocked` never triggers repair** — exit 2 means the checker
could not run, and asking the model to "fix" that trains it to fix the wrong thing; and
**golden-file drift is not a failure to silence** — the permissions/api gates' repair hint says
regenerate the artifact (never hand-edit it until the checker quiets), after which the diff is
the human checkpoint of builder-studio §6/§9.1. Repair prompts are recorded verbatim as user
turns in durable history, so the transcript stays truthful about who said what. Policy and
wording live in `gates.ts`, above the workspace seam, so the server and the dev CLI cannot
drift. Not built here: a dedicated `needs-review` emission for regenerated golden files, and any
UI affordance marking repair passes — both ride on later UI work.

**Smaller, take-if-passing-by:** spool over-cap tool output to a workspace file with a preview
(instead of dropping the middle — OpenHands and opencode both do this); repair tool-name case
mismatches locally instead of burning a round-trip; `store: false` on OpenAI requests; a
loop/stuck detector (OpenHands halts on ≥3 identical action/result pairs — cheap insurance in a
40-step loop). **Parked with a pointer:** aider's repo map — personalized PageRank over
tree-sitter symbol references, token-budgeted by binary search (~200 portable lines) — is the
upgrade path if `workspaceBrief` ever outgrows "file list + recent commits + last diff"; not
before.

**Explicit non-adoptions:** opencode's provider transform layer (scale mismatch, see §1
non-goals); a `task`/subagent tool for context isolation (wrong scale for single-vertical builds;
revisit only if evals show context exhaustion that compaction does not fix); favourites/recents
picker chrome (internal PoC, §1.1 of builder-studio).

## 4. Sequencing

Order chosen so billing correctness lands before optimisation, and each step feeds the next:

| # | Item | Why this position | Status |
|---|---|---|---|
| 1 | §2.2 snapshot generator (models.dev × LiteLLM cross-check) + rate card from snapshot: cache rates **and qwen context tiers** | billing integrity — the tier gap is an active undercharge; unblocks 3 and 5 | ☑ |
| 2 | H2 retry/backoff | turn survival — protects every other investment; self-contained | ☑ |
| 3 | H1 edit tool: strict apply + structured reflection (aider shape), format-per-model | biggest bill lever; weak models keep `write_file` by declaration, not by failure | ☑ |
| 4 | H4 cache key + qwen temperature | one-liners, default-provider quality | ☑ |
| 5 | H3 overflow → condense-and-retry (one code path), eager only off-Anthropic | needs `limit.context` from 1; cache-invalidation tradeoff says measure before defaulting on | ☐ |
| 6 | §2.3 credential-gated picker; `tool_call` filter on the Cloudflare list | UX correctness, not cost | ☐ |
| 7 | §2.3 family-based pairs | wait until the model list outgrows hand-editing | ☐ |
| 8 | H5 gate feedback: report into next-turn context + capped repair loop | the oracle must reach the model; step 1 was a live defect, not an optimisation | ☑ |

Each row lands as its own PR against this doc; the row's checkbox flips in the same PR. Evals
(builder-studio §9.6) are the referee for H1 and any claim that a harness change helped — token
usage per passing build is the metric, and the usage events already carry it.

## 5. Honest bounds

- Both catalogs are community-maintained list prices. The snapshot review (§2.2) makes changes
  visible, not automatically *correct* — billing-grade confidence still requires the one-time
  check against provider price pages, per model we serve. The two-source cross-check narrows the
  window, it does not close it (LiteLLM's own tracker shows price bugs clustering in reseller
  channels and newly-introduced pricing shapes).
- H1's win depends on the model holding the search/replace format. Aider's leaderboard bounds
  the risk globally (97–99% well-formed at the frontier, collapse below); our evals must bound it
  for the models we actually serve — the format-per-model flag is the mitigation, not a waiver.
- H3 and §3.1 are in tension: compaction invalidates the cache that the moving breakpoint pays
  for. OpenHands measured a full run costing *more* with condensation on a cache-friendly
  provider. Whatever lands must be measured per dialect, and "off on Anthropic until proven"
  is an acceptable outcome.
- Nothing here changes the §5.3 seam: every adoption lives in `AiSdkGenerator`, the tools, or the
  builder app — the generator interface and the workspace contract are untouched.
