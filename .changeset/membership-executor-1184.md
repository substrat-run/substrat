The kernel ships the membership executor (#1184): `registerMembershipExecutor(host, { actor })` consumes the `member.add-requested` event `@substrat-run/engine-invites` emits on accept, and effects the org membership and the invited role at the tenant node. It is tenant-level only (`level: 'scope'` is a type error and a refusal at run time): no single operation spans the directory and a scope store, and a scope role already has `assignScopeRoleBounded`.

- Nothing in the payload is taken as authority. The inviter is the kernel-stamped actor of the invitation's `invites.sent` event, and the membership is applied only if that inviter still holds, when the event is executed, every permission it would confer: the role's and the org's (read from the directory, `coversConferred` over the new `PermissionChecker.confers`). One invitation, one join: the request must be the first naming it. A sender demoted or removed between send and accept is refused, and so is a request naming another tenant, a joiner other than the one who accepted, a role the invitation was not sent for, or an invitation somebody else accepted first.
- The admin rows are written by the given platform actor, `onBehalfOf` the inviter, with `causedBy` the event id: the correlation id that joins the scope's half of the trail to the directory's.
- An executor handler receives a third argument, `ExecutorScope`: reads of the event's own scope (`history`, `covers`) that are safe from inside the handler on both adapters. On SQLite the handler runs inside the scope's actor, where the host's own reads would wait on themselves.
- A handler may return `refuseDelivery(reason)`: the delivery is journaled terminal with `refused: <reason>`, never retried, and listed by `executorDeadLetters`. It is a return value, so module code cannot produce one.
- `InvokeOptions.onExecutorOutcomes` reports what each executor delivery did in the call's inline post-commit tail (`delivered`, `retrying`, `refused`, `dead-lettered`, `inert`, `routed`), so a request can tell its caller the effect was refused or is pending instead of reporting success.
- `HostAdmin.applyMembership` applies a membership change as ONE directory unit (a SQLite transaction / a ControlPlaneDO method): an add's final "removed since" check, the membership, the role and both audit rows together, so an add and a removal serialize. A removal outside the seam wins at or after `occurredAt - MEMBERSHIP_REMOVAL_SKEW_MS` (5 minutes, ties to the removal); someone removed by staff less than that before accepting a NEW invite is refused, and the invite can be resent.
- Removal goes through the same executor: `member.remove-requested` (payload `memberRemoveRequestedPayload`, on `membershipEntity(principal)`) takes the role and the org membership away, bounded by the remover's own authority. Removal wins: an add is refused when the joiner was removed after it was requested, by a later `member.remove-requested` or by any `unassignRole` / `removeMember` admin row naming them. So neither a join still retrying nor a backlog from before the executor was mounted can re-admit someone who was removed.
- `readExecutorDelivery(ctx, { executorId, eventType, entity })` reads what an executor did with the newest such event, so a module can show the effect it asked for as it stands: `unattempted`, `retrying`, `delivered`, `refused` (with the reason) or `dead-lettered`.
- `membershipExecutorContractSuite` holds both adapters to it: accept, redelivery, rollback, the refusals, and the inline and retry-backstop paths.
