A confined caller (a tenant credential or a builder) no longer reads what an upstream, a store or a deployment answered when a failure reached installs that may not be its own (#2540). It sees only its own scopes and no upstream text; staff keep the text.

- **The answers.** These say that the step failed and carry a `reference`:
  - a prod promote's failed in-place serve (`502`, whose `detail` is now the fixed sentence), its store backfill (`storeBackfill.error`) and an export-break listing that could not be read (`exportBreaksUnavailable`);
  - a refusal to judge whom a promote or bind breaks (`503`), on every route that reaches it, the promote and `GET …/promote-impact` among them. The kernel's sentence names the app it could not read and that read's error, so the API answers it itself (`isExportBreakUnjudged`, new in the kernel);
  - on `POST /tenants/:tenantId/scopes/:scopeId/provision`, which a builder may call on any install of its own vertical, `storeError`, and a failed reconcile's answer for another tenant's install. A builder repairing its own tenant's install still reads the vertical's own answer, and a reconcile refusal (4xx) of another tenant's install is answered with the sentence and logged without filing a failure, as the 5xx backstop leaves a 4xx unfiled.

  Staff are answered the text, with the reference beside it.
- **Where the text goes.** To the `control-plane.unhandled` log line, with the request's method, path, vertical, version, tenant and scope, and to an ops-failure row with no tenant on it, so it never appears in a tenant's `GET /ops-failures`. Both carry the reference, which is always the platform's own. An upstream trace handle the text carries (`reference = <id>`, at most 64 characters) is kept only on the row with no tenant, at the start of its text, as `[upstream reference = <id>]`, so a bounded row keeps it. Any spelling of that marker in the text is neutralised first, and is never read as the handle, so only a genuine `reference = <id>` makes one. These are `withUpstreamReference`, `upstreamHandleIn`, `upstreamReferenceMarker` and `upstreamReferenceOf`, new in contracts. The same holds for every row the API files under a tenant, the backstop's included: its reference is the platform's own, and a handle in its text goes on a staff row beside it, under that reference. A row whose text the caller was answered in full still says what it said; staff, and no longer the tenant, find it by the upstream id. The one exception is a failed upload of a builder's own bundle (`deploy.upload`), which answers the builder the upload's text verbatim: its row keeps the upstream handle as its reference, so the builder still finds it by the handle the CLI printed (#559). Staff's `GET /ops-failures?reference=` finds both rows of the pair by either id (`OpsFailureFilter.referenceInText`, new in the kernel). `opsFailureReferenceWhere` is the one narrowing both adapters run, and it reads the marker only at the start of the text. A confined caller's search stays exact. The console's support-ticket copy offers Cloudflare's id when a row names one.
- **Rows a tenant reads back.** An ops-failure row attributed to a tenant says what the request was answered, whoever made it, staff included. That is only as clean as the answer, which is why the answers above changed. When the failure's own text differs, the API writes one failure with a `detail` (`OpsFailureInput.detail`, new in the kernel). Both adapters write it as the tenant's row plus a row with no tenant carrying the text, under one reference, and count it once: the issue's sample is the text, owned as the platform's, as the row it copies is, so a subject erasure reaches it on an id match. This covers the 5xx backstop's row and the rows of every answer above. The staff failure digest lists such a pair once, as its text, under its tenant. The console's failure view links a tenant's row to every row with its reference.
