A preview push or `scope bind` that moves a scope's data into another version's deployment now wipes the copy it leaves behind (#1722). Once the bind lands, the copy in the old deployment is wiped: emptied to a `carried_away` marker rather than reaped, so a later bind back to that version can carry the data in again. The bind expects the version the data was copied from, so of two pushes that read the same binding only one lands. The other is refused with a 412, and its copy is discarded unless the preview is now served from that same deployment (a CI retry of the same version). A carry also refuses an export from a scope that was re-pointed meanwhile, or from a store that was already wiped, before it restores anything. The three bind tails (preview push, `scope bind`, serving-pin repair) are now one.

A deployment built with this release also fences the wipe. A scope DO keeps a load stamp in `_substrat_meta` that never leaves in a dump. A carry's export (`/internal/export?stamp=1`) hands it over in the `x-substrat-load-stamp` header, with the store's write revision in `x-substrat-write-revision`, read in the same call as the dump, and stamps a store that has none. Every other export only reads. Every load replaces the stamp, with the stamp a carry names in `/internal/restore`'s new `loadStamp` field, or with none. The new `/internal/wipe-carried` route (`wipeCarriedLocal` on the host, optional in `VerticalScopeHost`) wipes only if the stamp and the revision are still the ones the carry read. So a rollback that restores into the old deployment while the cleanup is in flight keeps its data. A write that reached the old copy after the export (and so was never carried) keeps the copy too, recorded as `source-copy-kept`. The copy is then protected in its own store: every load into it, a bind back included, is refused (409) until staff resolve it through `GET`/`POST /tenants/:t/scopes/:s/kept-copy[/resolve]`. Staff can first pull the kept copy with `GET …/kept-copy/export`, under the governed export's rules (residency, masking unless `full=true`, access-logged), to reconcile by hand. The resolution is either a discard, or a restore forward over the live store, acknowledging the live writes it replaces. A restore forward is fenced on the scope's binding throughout and discards the kept copy only once its data is in the store the scope still routes to. A carry that finds its source changed in any way since its export, while the scope routes elsewhere, keeps it too, and a third action, `release`, clears the marker of a kept copy that turned out to be the live store. All three are logged through the new `HostAdmin.recordKeptCopyResolution` (admin action `resolveKeptCopy`). A copy the carry wiped refuses writes, so a stale request still routed to it lands nothing. A copy the carry wipes or keeps is marked a copy (#2005) whenever the directory says the scope is not primary, a copy made before the marker included, and marking a store a copy never counts as a write the carry missed. An older deployment answers 404 there, and the wipe falls back to an unconditional load of the marker through `/internal/restore`. That path is guarded by a route re-read and by the rollback checking its own store for the marker.

The restore into the new deployment is fenced the same way. A carry reads the destination's marker (`/internal/load-marker`: the load stamp and a write revision that every write advances inside the transaction that commits it, an in-place update such as a drain receipt included) before checking the binding again, and sends it back as `expect` on `/internal/restore`. The restore is refused (412) inside its own transaction if that store was loaded or written since, so a retried push held before its restore never overwrites the store the first run bound and wrote to. An older deployment answers 404 there, and the binding read right before the restore is then the only guard. Only a 404, a 501 or an HTML shell served as `text/html` reads as an older deployment. A wipe or marker answer that is lost in transit, truncated or otherwise not valid JSON is a failure, never the unconditional fallback. The cleanup is best effort: a carry that fails between its restore and its wipe can still leave a copy, and reconciling those is not done yet.
