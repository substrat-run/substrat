A Microsoft 365 connection can read and write files in one Teams channel's folder of the tenant's SharePoint site (#2101).

`@substrat-run/connector-microsoft365`: `bindMicrosoft365Scope` binds a scope to one folder, named by its drive path under the site's default document library and held by its item id from then on. A vertical writes by emitting `microsoft365.channel-files-requested` (`microsoft365FilesRequested`: a `directory` under the folder, up to 20 `files` by attachment id with each attachment's `size`, and a required `conflict` of `replace`, `rename` or `fail`). Files are at most 50 MB each and 100 MB per event, checked on the declared sizes before any byte is read (a declaration that is not the attachment's own size is refused once that attachment is read, since the platform hands over its bytes whole), and an attachment may be named once. The dispatch uploads the files one at a time, in one request up to 4 MB and by upload session above, and keeps a ledger keyed on the event id. A redelivery takes an existing file as its own only when this app wrote it and its size and QuickXorHash are the bytes being sent. A `rename` conflict uses a suffix derived from the event, never one Graph picks. `sweepMicrosoft365Files` follows the library's change feed a page at a time, saving where the next page starts after each landed page and stopping at a page budget per call (`SYNC_PAGES_PER_CALL`); a folder newly inside has its children read a page at a time under the same budget. A held item the feed does not account for (one a full pass never presents, or one a page shows somewhere it cannot place) is looked up in the drive on its own before anything lands for it, under its own budget (`SYNC_VERIFY_PER_CALL`). An item is deleted only on an answer about that item: its own deleted facet in the feed, or its own lookup finding nothing; never on a folder above it or a re-read's silence. A transient lookup error stops the pass with nothing deleted; a refusal that will not pass by itself (400, 403, an enclosing folder that cannot be read) keeps the item held, lets the pass finish, and is counted in `lastSync.unplaced`. It is asked again only on a later full pass or when the feed mentions it again, at most `MAX_UNPLACED_ATTEMPTS` times; after that it stays held as last seen, never deleted, until a re-bind or a full pass with fresh state. A folder's own answer lands even while it still holds such items, which stay held. It lands each change in the folder through the binding's operation as the connection (`microsoft365ChannelChange`: `upsert`, `content` and `delete`), at least once and keyed by item id, with file contents uploaded as attachments on the entity the operation names. A path outside the folder is refused before Graph is called. Items outside the folder are never stored or logged. A deleted folder makes the binding refuse rather than fall back to the library root, and an unbind or re-bind during a pass is never written over. `registerMicrosoft365FilesConnector` and `declareMicrosoft365FilesConnector` register the dispatch on a host that runs it, or for routing only on one that does not.

`@substrat-run/control-plane-api`: the connection bindings route takes a `folder` for a Microsoft 365 connection, and only for one. `@substrat-run/contracts`: the binding audit entry carries it. `@substrat-run/control-plane-client`: `ConnectionScopeBindingInput` gains an optional `folder`. `@substrat-run/cli`: `substrat connection bind` takes `--folder`.
