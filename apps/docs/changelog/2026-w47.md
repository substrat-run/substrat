# Week 47 · 16–22 November 2026

The week's theme is **knowing the number instead of estimating it**.

The platform pays its infrastructure bill for every tenant's usage and, until
this week, could attribute almost none of it. That is not an accounting
inconvenience — it means a plan cannot be priced and an outlier cannot be
caught. So the scheduled pass now keeps a daily rollup of every billed
dimension, attributed through the directory to a tenant, a vertical and a
scope; a scope's own object counts the rows a vertical's operation wrote apart
from the rows the platform's own work wrote in the same object; and a dated
markup schedule turns that cost into a price without ever repricing a past day.

The first measurement is also why the second-largest change of the week
happened. Rows written were about 95% of the cost, and **preview forks were
about 84% of it** — a fork copies every row of its source, and each row copied
is roughly five and a half rows written at the destination. So previews stopped
being automatic: a pull request gets a **Build preview** link rather than a
build, and a fork can copy a sample of production under a row cap.

The other half of the week answers a different question with a real number.
**Art. 17 of the GDPR — "delete what you hold about me" — has been shipped for a
while; Art. 15, "what *do* you hold about me", has not.** It does now, from the
dashboard, reading through the same plan erasure uses. Beside it: a second store
platform landing the same provider-neutral commerce records as the first, a
vertical taking a payment through its tenant's own Stripe account, a connection
keyed on the account its probe names rather than on the row it was pasted into,
and every refusal in the demos and the scaffold answering as a problem document.

## What your app costs, measured rather than estimated

The source is the infrastructure provider's own analytics — the numbers the
account is invoiced on, so a cost basis rather than an estimate. They answer for
**90 days** and then the day is gone, which is why the rollup had to exist before
anything else: until it did, history aged out one day at a time.

**One row per closed UTC day, per script, scope, object class and dimension**,
holding cost inputs only and never a price. Worker CPU and Durable Object
requests come from sampled datasets and carry their 95% confidence interval;
rows read, rows written, storage write units and duration per object come from
an aggregate and carry no interval.

**Attribution runs through the directory, in the transaction that records the
day.** An object maps to a scope by the id the directory recorded for it; a
script maps to its vertical, its version and the vertical's owner *on that day*.
An object no scope was recorded for — a config, identity or sweeper object, or a
scope reaped before its id was ever known — is reported apart, with no tenant,
rather than guessed at. Each scope's object id is learned from the script that
holds its data, by a sweep phase that also backfills every scope that already
existed.

A day read before its scopes' object ids were known would otherwise be lost
forever, because a day is read once. So each cost row keeps its object id, and
recording a scope's id re-attributes that object's unmapped rows in the same
transaction. **Deploy order no longer decides which days keep a tenant.**

### Platform work and your work, in the same object

A scope *is* a Durable Object, and the provider bills SQLite rows per object.
Its analytics therefore cannot tell a vertical's operation from the platform's
own work in the same object — a preview fork's load, a migration pass, a drain, a
purge, a sweep. The scope host now counts that itself: each statement's
`rowsWritten` and `rowsRead` (the billed values), attributed to the RPC entry
whose async context ran it, written as **one analytics data point per
invocation**. Nothing is written to SQL, so measuring writes no rows.

Two findings worth knowing if you ever read these numbers yourself. A Durable
Object's cursor for a multi-statement `exec` reports **only the last statement's**
rows — two inserts report one row, and a select before an insert reports zero
read. The meter therefore runs such a call the way the kernel's statement
splitter cuts it and counts each piece, only when the pieces provably reproduce
the original. And the migration pass and capture expiry are counted apart from
whichever entry happened to trigger them.

### Cost becomes a price, and a past day keeps its markup

The markup schedule is **data, not code**: a default, plus overrides per tenant,
per billed dimension and per kind (live or preview), the most specific row
winning. Rows are **dated and never edited**, so a past day is always priced at
the markup in force on that day and changing a rate never reprices history; a
null row ends an override at its level. Price is computed at read with the
decimal helpers, never floats, and the rollup stores cost alone.

What a tenant sees is the price. Staff see cost, markup and price side by side.
Every change is an admin-log row, and a row taking effect before today is
refused. The seed is read *beneath* stored rows rather than inserted, so
restoring a directory cannot collide with it.

**The schedule reprices nothing on its own.** The seeded defaults are 100%
generally, previews at cost, and model calls at 30%, which is what the platform's
model ledger was already charging. **One rate did move**: the builder studio was
carrying its own hard-coded 20%, and it now reads the same row as everything else,
so a non-zero model call in the studio is priced at 30% where it used to be 20%.
That is the whole point of having one markup mechanism instead of two, and it is
the only price that changes this week.

### A second account of the model calls

The model usage ledger is **self-reported**: a vertical's own model host builds
the usage line, and only a line raised as a model-usage intent reaches the
ledger at all. A hosted vertical whose record hook merely logs the line costs
real money and appears in no ledger.

Each closed day is now folded against the provider's own gateway and inference
analytics — a second account of the same calls, kept by someone other than the
caller — per tenant, scope and model id, into **matched, discrepancy,
ledger-only and gateway-only** rows. Beside them: gateway calls with no
attribution, calls for a tenant another directory holds (the environments share
one account), and inference calls that went through no gateway at all, which
nothing can attribute.

**The ledger is never corrected from either source.** Discrepancies, gateway-only
rows and the unattributable total are filed as staff failure rows. The point is
to make the gap visible, which it now is; closing it is separate work.

## Previews happen when you ask for them

Two numbers made this change. A preview forks production's data and a fork is
billed per row written: one vertical previewing every push to every pull request
wrote about **83 million rows in a day**. And hosted builds run one at a time per
vertical, so a preview of every push queued in front of the merges that deploy
production — over four weeks of this repo's own workflows, **queue wait was 47% of
a build's wall time, and 71% in the latest week** (median 7.2 minutes queued
against 4.3 running).

So the default moved to on-request everywhere a workflow is written:

- **The generated workflow takes `previews: 'every-pr' | 'on-request'`.** On
  request, `labeled` joins the pull-request trigger and the preview job runs only
  for a pull request carrying the `preview` label — and on a `labeled` event, only
  for that label. Removing the label stops updating the preview; closing the pull
  request still reaps it. `every-pr` is byte-identical to what it was.
- **A pull request gets a comment with a Build preview link** instead of a build.
  The page itself changes nothing on a `GET`; pressing the button checks that you
  may deploy the vertical and labels the pull request through the App.
- **`substrat init --ci github --previews on-request`** writes it, and
  `--previews every-pr` keeps the old behaviour.

The link only goes on a pull request that could actually start the workflow. In a
monorepo, the repo link records the package path the workflow is filtered to, and
a pull request changing only other packages — a dependency bump among them — gets
no link that would say *Building…* for thirty minutes and then give up. The path
list is one export shared by the generated `paths:` filter and this check, so the
two cannot disagree. A `labeled` event on a *closed* pull request builds nothing,
since only `closed` reaps and that preview would have outlived its pull request.

### A fork can copy a sample, or refuse to copy at all

Two options make a fresh fork cheaper, and the default — a whole copy — is
unchanged:

- **`--sample <n>`** reads the newest *n* rows of each table, among those whose
  declared parents it keeps, plus the spine about them. The first page fixes each
  table's floor and echoes the plan; every later page uses it, so the sample is
  stable across a paged copy.
- **`--max-rows <n>`** counts the rows a copy would move *before* anything is
  reaped or provisioned. Over the cap the create is refused with a `413` naming
  the count and the largest tables — or copies `--sample-over-cap` instead.

All three are also optional repository variables in the generated deploy
workflow. Separately, a copy into a scope's store now reads the source's database
size first and refuses a scope over 4 GiB with a `413` naming the size: a staged
load holds the copy twice while it commits, so a larger scope used to copy every
page and only then fail at the commit. Backups and the post-bind re-carry are not
gated.

## What an app holds about one person

The erasure half of a data-subject request has been shipped for a while. The
access half — Art. 15, *what do you hold about me* — lands this week, and the
design decision that makes it trustworthy is that **it reads through the same plan
erasure uses**, with a contract test that walks the read, then shreds the same
subject, and holds the two to each other's counts. It is not yet the whole of what
erasure reaches: a `custom` entity, which erasure reaches only through a hook that
can write, has no read-only twin to call, so the package **names** it as unreached
instead of reading it.

**The read, in the kernel.** `HostAdmin.readSubject` pages what one scope holds
about one data subject: every outbox event keyed to them — PII class `none`
included, an erased event as its envelope — then the whole rows of each declared
blank-or-delete entity, matched by the same predicate erasure uses. Custom
entities are **named rather than read**: erasure reaches them only through a hook
that can write, and access has no read-only twin yet, so the package says what it
could not reach instead of implying there was nothing there. Both adapters carry
it, with a partial index on the spine serving both this read and erasure's
redaction.

A reaped scope is refused **before its storage is touched**. The scope assertion
admits a reaped tombstone, so a subject read could otherwise have woken the
object, handed it a fresh empty spine, and answered "nothing held" about a scope
whose data an irreversible reap had destroyed. Both hosts now read the scope
record first and refuse with a conflict. On the shared control plane, a scope
bound to a vertical lives in *that* deployment, so the read also refuses to
answer from its own namespace — which would have been incomplete, and would have
looked like success.

**The request, in the dashboard.** A team's owner or admin runs it from a new
**Personal data** section of the app's Data tab, behind `dashboard:subject-access`.
The form takes the person's id, a one-line reference — *not* their name or
address — and an identity confirmation, and hands back a JSON package and a
self-contained HTML page with no script in it.

- **Other people are pseudonymized.** Every id in a subject column that is not
  the subject's, and every actor who is not the subject, is masked with a fresh
  salt per package; the package lists which columns it changed, and an actor's
  *kind* stays visible. A subject column holding another person's id as a number
  was being copied through unmasked, which the review caught: any non-null value
  that is not the subject's is masked now.
- **The package says what it is missing.** Categories of data, storage locations,
  the entities it could not reach — and recipients as `not-available`, until the
  disclosure register exists, rather than an empty list that reads as *none*.
- **A scope with a platform store is refused** with a `501` naming the binding,
  until a store driver can answer the access question. The guard judges the export
  path's whole reach, so a binding an *earlier* version declared that still holds
  rows refuses too.
- **A bigger subject gets a `413`, never a truncated package** — fifty pages of a
  thousand items is the ceiling. The refusal is honest on both paths: no package,
  no receipt.
- **Every request is recorded** as an admin-log row whose receipt carries counts,
  the reference and the identity confirmation — never content — with the signed-in
  member named through `onBehalfOf`, and a sentence in Audit › Activity under their
  name. Each page read is logged once, by whichever side served it.

The package is exempt from the jurisdiction gate the bulk exports carry, because
Art. 15(3) requires this copy to leave, and the receipt records that exemption
rather than hiding it.

## A second store platform, in the shape the first one landed

A read-only **Shopify** connector now lands the same provider-neutral
`commerceChange` records as the WooCommerce connector, so **one landing operation
in your vertical takes either store's products and orders**. The shared
commerce-source suite moved into `@substrat-run/contract-tests` now that two
connectors run it — which is the real test of whether the shape was neutral or
just WooCommerce-shaped. One assertion had to change to find out: "a product
without variants" now means *one untitled, optionless variant*, and the rule that
such a variant reuses the product's id moved into WooCommerce's own mapping test,
because a single variant's id is the store's to give.

The mapping decisions are written down where a reviewer can argue with them. Ids
are the numeric tail of the GID, the same number the admin shows in its URLs.
Stock status is **derived**, since Shopify has no stock-status word: untracked is
in stock, a positive count is in stock, and zero or below is on backorder or out
of stock depending on the continue-selling policy. Order money uses the currency
the customer actually paid in. For a **tax-inclusive** shop, line total and tax
come out exact by subtracting the store's own tax lines — and exactly one figure
is derived rather than taken from the store: a discounted line's pre-discount
subtotal, computed and rounded half-even.

Two limits the connector refuses to paper over:

- **Orders are reconciled for deletes only when the app holds `read_all_orders`.**
  Without it the store hides orders older than 60 days, and that looks exactly
  like a delete. The probe reports whether order history is full or limited.
- **Changes from the last two minutes are left for the next pass**, because a
  store's search index can lag a save.

It has not been run against a real shop, and the connector's page says so.

### The WooCommerce half

- **Stock levels** for products and variants, read from rows the walk already
  reads, so no extra request: managed-stock, the quantity (null when the store
  does not count it — never zero), the store's own status word, and a flag for
  when one count covers every variant.
- **A trashed or deleted record is reported.** An hourly reconcile asks the store
  about the ids it handed out, confirms each unaccounted id with a single read
  that must answer the store's own invalid-id 404, and lands each removal as
  `removed`, with `trashed` or `deleted`. An id never delivered is never asked
  about; a removal is marked reported only once it landed; a trashed id stays
  watched until it is restored or deleted for good.
- **One record that cannot land no longer stops the walk.** An unreadable row is
  skipped at once; a row whose landing keeps failing stalls its own resource for
  three passes and is then skipped. Products, orders and the reconcile run
  independently of a stalled record. Skipped rows are kept on the binding with
  their error and retried by id.
- **A variation with no SKU of its own reports none.** WooCommerce fills an empty
  variation SKU from its product, so every SKU-less variation arrived carrying the
  same SKU and read as a duplicate.
- **A scope can connect its own shop.** The registration is scope-owned: a store's
  worker upserts its shop as the scope's own connection and binds it through an
  on-request landing. Every binding records the owner beside the store, and
  binding a scope's own connection to any *other* scope is refused at bind and
  again at the sweep, before the store is asked. Tested end to end with two
  sibling stores: neither receives the other's records, and revoking one stops
  only that one.
- **A scope can read why.** `listBindings({ health: true })` answers each
  binding's connector-kept health — the records its walk is waiting at, the ones
  it skipped, whether it has caught up — and lists the tenant's connections bound
  to the scope too. Opt-in, because older hosts parse that answer strictly.

### And a failure is filed where the tenant can see it

A connector binding that fails a pass is now filed as a **pair**: a tenant row
carrying the scope, in the platform's words plus the connector's own sentence,
and staff's row with the failure's raw text. The app's Failures view and fleet
health read failures narrowed to the app's scope, so an app's own connector
failures appear there. A failure naming no scope stays staff's alone.

What the tenant's row is allowed to say is decided in the kernel: a **4xx the
vertical answered** may be quoted, never a 5xx, never the platform's own
credential check, never a non-problem body, never an uncoded in-process throw. So
"your app refused this landing because…" reads as a cause instead of *did not
land* plus a reference.

Beside it, the platform's calls **into** your app are now in your Logs. These go
over an internal surface that no request line covered, so a connector's landings
— failed or not — showed as nothing at all. Each call writes one async invocation
line of the new `connector` kind, carrying the ids, the operation, `connection`
as who it ran as, the outcome, the problem code and the emitted count and types.
Never the provider's input, and never the error's text.

## Taking a payment through your own Stripe account

A vertical can now take a payment through **its tenant's own Stripe account**. The
worker opens a hosted Checkout Session inside its own request, the buyer pays on
Stripe's page, and the outcome lands back in the scope through an operation the
vertical declares, as a provider-neutral `paymentChange` — a neutral status
(`open` → `processing` → `paid` | `failed`, or `open` → `expired`), your own
reference, a decimal amount, and `live`, so a vertical can refuse a test-mode
payment in production. Built like `commerceChange`, so a second payment provider
lands the same records. There is **no engine**: orders, and what "paid" unlocks,
stay the vertical's.

**One reference is never paid twice through this door.** The same ask while the
session is open answers the same session; a changed ask closes the open one
first; a reference already paid or settling is refused; and concurrent asks are
serialised by a compare-and-set claim on the reference. Amounts convert to minor
units exactly — never rounded — and the currencies that do not fit that rule are
refused by name.

**The webhook is a hint, not a source of truth.** After the per-connection URL
token and Stripe's signature over the raw body, the event and the session are
both read back from Stripe, and only Stripe's answer lands. A leaked signing
secret lets a caller trigger a re-read; it cannot land a fabricated outcome.
Sessions this connection never opened do not land at all.

The relay runs behind the binding relays' gate — a proven caller and a **primary**
scope — so a preview or a fork can never charge anyone. It goes through the one
live payment connection bound to the scope; none bound, or more than one, is a
`409`.

Stripe has not been exercised against a real account either, and the connector's
page says which readings are the ones worth a test-mode run.

**Which account an install charges through is now a choice.** The landing pass
binds an install to the connection already bound there, else to the oldest active
tenant connection — so a second account no longer binds everywhere and a tenant's
choice is never undone. A *Use for checkouts* door on the app's Integrations tab
moves an install to another account: the chosen connection is bound first, then
the others come off the install. A refused bind changes nothing, because it fails
before anything is taken off. **A change that fails later can leave more than one
connection bound** — the new binding is rolled back only while nothing has come off
yet. Checkout refuses with a `409` once more than one **active** connection is bound,
rather than guessing which account to charge — so a stale one left in an error
state does not stop a charge reaching the new account. The install's choice read
lists everything still bound, that one included, so you can choose again once the
cause is fixed.

## A key is keyed on the account it opens

This is the week's quietest correctness change and probably the one most likely
to surprise someone. A provider whose credential does not itself name its account
— a Stripe secret key — had no account leg on the connection upsert, so **every
paste rotated the one unkeyed row, even a key for a completely different
account**.

A registration can now declare that the account comes **from the probe**: the
relay probes the candidate credential first and keys the connection on the
account the probe names. The same account rotates in place and keeps its cursors
and state; another account becomes a **second connection**; a probe that cannot
name the account **stores nothing**. A connection made before this, holding no
account, is left exactly as it is.

- **Stripe** is pinned to one account *and one mode*. The probe names the account
  id and whether it is live or test, with the account's own name as the label; the
  cheapest call that names it is the account read, and a restricted key without
  that scope is named by Stripe's own refusal instead. A key for the same account
  and mode is a rotation and keeps everything. **Another account, or the other
  mode, is refused with a `422`** telling the tenant to connect it as a new
  connection — so *going live is a new connection*, and the docs say what a new
  connection does not carry over. A Stripe that does not answer stores nothing, so
  every stored key is pinned.
- **WooCommerce** is keyed on the store, taken from the store's own `home_url`
  without the scheme or a trailing slash. A key for the same store rotates its
  connection and keeps its cursors; a key for another store becomes a second
  connection. Every open names the store, recorded on the binding. For a
  connection made before keying, a candidate is judged against the address that
  connection was pasted with, and another store's key is refused with nothing
  stored.

The webhook row and each checkout row also record the account they were written
under, so a key that reached a connection by some other path reads none of
another account's checkouts. A checkout Stripe no longer has — test data deleted,
account closed — is held as missing and never asked about again, and **its
reference stays refused while a live payment may have been taken**.

## A team that provisions tenants

The managed-tenant work finished this week: a team can stand up a tenant for
someone else, with sign-in at its own identity server, and take it down again
without leaving anything behind.

- **The requester's verified address owns the new tenant.** A request may name the
  address the requester's own sign-in verified. The new scope's owner seat then
  opens **no first-sign-in window at all**: only a sign-in whose issuer verified
  that same address claims it, by the same rule a member invite uses. Without the
  field, the seat keeps the 15-minute window a dashboard install gets. The address
  rule moved into `vertical-auth` so the owner seat and the member directory share
  one copy of it.
- **It fails closed.** A deployment whose provision hook does not *report* the seat
  reserved — an older one, or one that drops the field — is refused with a `501`
  before any write, rather than quietly opening the 15-minute window and answering
  `201`. A worker that resolves its own callers now claims an address-reserved
  seat through a new `resolveSignedIn`; `/api/me` says a seat is reserved while it
  is, reading a flag and never the address.
- **A managed tenant gets a default hostname**, bound after the tenant is
  activated, with every other declared surface beside it. A name another scope
  holds falls back to the same name tailed with the scope id's last six
  characters, and a retry keeps the name an earlier pass bound — and finishes
  activating one a previous pass left pending, rather than reporting an address
  that does not route.
- **It signs in at the manager's own identity server.** A request may name one of
  the manager's team auth-servers, checked before any write to be an active
  hostname of an active scope in the manager's tenant running a vertical that
  provides an OIDC issuer. The drain then registers a client there, delivers it as
  the scope's auth configuration, and registers the scope as a **place** under the
  managed tenant's key — so a person's account page at that issuer lists every
  managed tenant they hold a principal in, invited ones included, and nothing
  else. The client is registered **once**, keyed by scope, so a retry reuses it,
  and federated sign-*out* works because the redirect set is delivered in the same
  final transaction as the place.
- **It is removed at the end.** Deleting or reaping a managed tenant removes its
  place and client at the manager's issuer — and the ordering got the attention it
  needed: the removal runs inside the storage reap, after the claim, copy check and
  store preflight and *before* the unroute and wipe, and before the retention
  reap's store fence, so an issuer that cannot be reached stops the reap while the
  data is still there rather than after it is gone.

## Every refusal is a problem document

The last of the hand-rolled error bodies is gone. The demo verticals' and the
scaffold template's routes that still answered `{ error }` now answer
`application/problem+json`, with `error` kept beside `detail` so nothing that
reads the old field breaks. The router, `vertical-host` and `vertical-auth`
converted too, and the pending list in the lint that holds this is now empty —
which means a new unconverted refusal is red rather than merely untidy.

Converting them surfaced a real bug in the helper. **A declared code now outranks
a fault phrase in the message.** The classifier ran its platform-fault check
first, and that check pattern-matches the message, so `substratError('conflict',
'…transient issue…')` answered `502 platform fault` instead of `409`. Fault
phrases now apply only to a throw that declares no code; the runtime's own
retryable and overloaded flags still mean `502`. Three routes that echo
caller-chosen text — an unknown operation name, an unknown path, a column named
in a file — were answering `502` for exactly this reason and now refuse directly
with the status they decided.

## An app's own mail-in address

Inbound mail became self-service. An app's mail-in address is in **Settings →
Integrations** with its counts, and a team owner or admin can get one, replace
it, turn it off, and set who may send. The read is behind the same check as the
write, because the address *is* a capability. Every act names the signed-in
person in the admin log, and the card keeps a failed read and a refused act
apart, so a refusal stays in its dialog instead of vanishing behind the read that
follows.

Each address accepts at most **60 messages a clock hour and 250 MiB a UTC day**,
and past either, mail is refused at SMTP time. The counting is the careful part:
it happens by compare-and-set *after* every other check, so a refusal is no
oracle for which addresses exist and a duplicate never counts. A quota row
remembers the messages it charged today, so two copies of one message arriving
together are charged once and a retry after a failed store reuses its charge
instead of being refused at the limit it set itself; and a message that read the
clock just before an hour or a day turned is counted in the newer window it
finds, never writing the older one back over it.

## Code reviews, priced and measured

The hosted review runner got the two things it needed to be run on somebody
else's money.

**A measurement.** Nineteen seeds over real files at a pinned commit: a
known-bad change for every checklist item, real bugs no item covers, and clean
changes — three of them twins of a bad seed with the defect fixed, which is the
only way to tell a reader that finds things from a reader that says things. The
scorer and every seed's integrity run in CI; the paid read is an opt-in probe
with a budget it refuses to exceed. Making the corpus honest took several
rounds, and the rounds are the interesting part: eight seeds edited a model and
left its emitted artifacts stale, which no real push does, so **a reader that
noticed was right and was being scored wrong**; three seeds added an operation
with no test, so the missing-test finding there was correct too and is now
allowed. Two seeds carried a second defect they were not about.

**A limit.** A per-tenant daily spend limit on reviews, summed from the ledger
over one UTC day as the would-be cost: staff set it as the review entitlement's
quota, else the plane's default, and **unset fails closed**. The model host's
guard refuses before the call, an unpriced review model is never called at all,
and intake answers `429` once a tenant is already over. Reviews priced at zero
are shown beside what they *would* have cost, and a capped read is marked as a
lower bound on every figure rather than presented as a total.

The reader's call now **streams**, with its output cap raised to 32k: the gateway
was closing unstreamed calls at about 60 seconds and reasoning models were
spending the old 8k cap, so most corpus reads came back incomplete. A stream that
fails partway throws the provider's own error and records nothing, rather than
returning the partial text. And a streamed call now asks for usage explicitly —
without that, a provider that waits to be asked returns none, the line is
unpriced, and the review escapes the spend limit it was supposed to be under.

One checklist item got measurably better: of one model's seventeen false
findings, sixteen were the same item firing on a source file edited together with
its re-emitted artifacts. That item now names the pairs, counts an artifact
listed as not-sent as present, and raises only a hand edit, a stale artifact, or a
visible disagreement.

## A screen that waits for its answer

Both consoles had the same bug in several places: a list that had not loaded yet
drew "nothing here", and a list whose read **failed** drew the same thing. An
empty state is a claim about the data, and neither of those is a reason to make
it.

The dashboard now holds its reads as one request state — loading, error, or ok —
each settling on its own, through a shared hook and a shared skeleton. The
console's fleet walk is one state instead of four empty arrays, so the sidebar
badges get a count only once the read has answered, a failed re-read keeps the
last answer, a failed first read draws one error with a retry, and a failed
refresh keeps the data and says so. Only the newest read writes, so a stale page
cannot overwrite a fresh one, and a refresh reports its own outcome.

**The dashboard also has a mobile layout.** Below 768px the sidebar becomes a
drawer behind a menu button — announced as a modal dialog, with the page inert
and Escape returning focus — the top bar keeps only the current crumb, gutters
shrink to 16px, and tables stack. The stacking needed one more pass than
expected: a stacked row loses the header that said what its numbers were, so
cells whose value does not name itself now carry a label drawn in front of the
value on phones only, while the header row stays *visually* hidden rather than
removed, so a screen reader still has its column headers.

Also on the team's Integrations page: the connectors **your own apps declare**,
listed after the first-party cards, connectable only from those apps — one card
per declaration, because two verticals may declare the same provider with
different fields and deduplicating by name rendered a form the chosen app's door
then refused. A live connection no vertical declares any more is listed formless,
with a team-level door to withdraw it, since deleting an app revokes nothing and
such a connection used to be listed with no way to remove it.

## Six changes to notice

1. **Pull-request previews no longer build on every push.** A repository set up
   from now on gets `previews: 'on-request'`: a pull request gets a **Build
   preview** link, or you add the `preview` label. A link stored before this
   change, and a repository that already carried the workflow, keep `every-pr` —
   including on a re-run of setup. `substrat init --ci github --previews every-pr`
   writes the old behaviour deliberately. If you were relying on a preview URL
   existing for every pull request, it will not.
2. **A pre-promote snapshot expires after 30 days.** A fork-taken-before-promote
   is now born with an expiry, on both hosts and at both call sites, so the
   snapshot collector reaps it — a half-made one included, since the row is
   written first. A staff route moves or pins a copy's deadline, and a backfill
   gave every existing archive fork `max(created + 30 days, now + 7 days)`. If you
   were treating those copies as an archive, pin the ones you want.
3. **A Stripe connection is pinned to one account and one mode.** A key for
   another account, or a live key replacing a test one, is refused with a `422`
   rather than rotating the connection you had. Going live is a *new* connection,
   and it carries over no checkouts, no webhook row and no state. The same shape
   applies to WooCommerce, keyed on the store its probe names.
4. **`requestSignatures` accepts a single party, and every party now needs a
   contact.** The one-party refusal existed because the signing connector used to
   map the primary party to an author who is never invited; it has had a
   non-signing sender party of its own for a while, so every party you name is
   invited — which is also why the primary now needs a contact. The reachability
   check runs **before the instance freezes**, so a party with no contact is
   refused at your call instead of dead-lettering in the connector afterwards.
   This is why `engine-protocol` took a minor.
5. **A declared error code outranks a fault phrase in the message.**
   `substratError('conflict', '…transient issue…')` used to answer `502`; it
   answers `409`. If you were relying on a message phrase to escalate a refusal to
   a platform fault, declare no code instead.
6. **Demo and scaffold refusals are problem documents.** Bodies are
   `application/problem+json` now, with `error` kept beside `detail`. A client that
   reads `detail`, `type` and `status` keeps working; one that switches on the
   response's *shape* should read the problem document.

## For hosted operators

- **The connector sweep can no longer take the scheduled pass with it.** One
  connection's sweep was exhausting the cron isolate on every pass, and because
  the reset left no sweep row, the next pass ran it again — so every phase after
  it (the event and access-log drains, the digest, the hostname reconcile, the
  directory backup) silently stopped running. The connector phase is now separable
  and runs **after** every other phase; each sweep notes an awaited attempt row
  before its work, and an attempt with no outcome backs that connection off (30
  minutes, doubling, capped at a day) and files a staff failure on each retry.
  `CONNECTOR_SWEEP_PAUSED` names connections to skip. A sweeper's `fetch` is held
  to 64 MiB of response bodies and ten minutes, counted while bodies stream, with
  a buffered read holding its bytes once. The failure digest's watermark skips the
  connector rows now written after it, so a tail of them cannot move the window
  past a failure filed earlier in the same pass.
- **The access-log drain repeats until it catches up.** One 500-row batch a pass
  was outrun by the ~720 access rows the plane's own sweep writes per pass, so the
  backlog only grew — 944 000 rows and eight days behind at its worst. It now
  repeats ship, stamp and prune while a batch comes back full, up to
  `accessLogBatchesPerPass` (default 8).
- **New switches.** `SCOPE_WORK_DATASET` and the scope-work bindings the uploader
  injects; `MODEL_RECONCILIATION`, production only; `REVIEW_DAILY_SPEND_LIMIT_USD`
  and `REVIEW_MAX_OUTPUT_TOKENS` (32k). Staff read the cost rollup and load an
  older snapshot day over `/meters/cloudflare-costs`, driven by a backfill script
  that is a dry run by default; the markup schedule is staff-only
  `GET`/`POST /markup-schedule`.
- **Releases publish in waves and wait for npm to actually serve each
  dependency.** Publishing one package at a time in topological order was not
  enough: npm served a CLI version before the contracts version it pins, and the
  scaffold check got a 404 on a tarball the packument already listed. Accepting an
  upload is not serving it. Each wave now polls until every workspace dependency
  it pins is listed *and* its tarball answers 200, bounded at ten minutes and
  failing with each version named; the scaffold check waits the same way.
- **The builder's sandbox container has a rollout grace period.** It was rolling
  out with a grace period of zero, so a release terminated a source build's sandbox
  three seconds after the build claimed it. An hour's grace spares every build — a
  release of ours, and a tenant's push during one — and because a per-command cap
  bounds no build, a build now takes a deadline when it is claimed and its reads
  and writes are refused once it is spent.
- **A push and a rollback across a pre-fence script can no longer lose both
  copies**, and the sweep settles a left-over entry on such a script as retained
  instead of failing every pass. A carry whose bind landed no longer wipes its own
  destination once the route has moved off it.
- **A managed tenant's sign-in is removed in the right order** relative to the
  store fence and the wipe, as above. **The social relay serializes handing out a
  secret**: a rotation is a compare-and-set on the generation the caller read, a
  two-minute lease refuses every other rotation, and every delivery names its
  generation, so an install refuses a secret older than the one it holds and a
  stuck install heals on its next reconcile. The relay also now recognises
  installs of the platform workspace's Auth Server lineage, which it had been
  refusing as "not an Auth Server install" since the bare verticals were retired.
- **`scripts/env-provision` took its review fixes**: the bootstrap token is
  removed from the environment as it is read so no child process inherits it,
  production's shared deploy secret is no longer replaced on every run and its
  deploy token is not rolled without an explicit flag, CI variables go through an
  allow-list pinned to the origin repository, and a dry run mints nothing.
- **Deploys push with the workspace CLI.** A deploy running the published CLI
  judges `main` by the *last release's* layer rules while CI judges it by `main`'s —
  so a merge passed CI and its deploy's push then refused the same file. Every
  deploy now runs the CLI built from the checkout, and a lint refuses a workflow
  line that reaches for the registry copy.
- A snapshot repository per builder project, pruned to the newest twenty and
  deleted with the project, replacing one repository per build that nothing read
  and nothing deleted. The Operation facet lists its top 7 where other facets keep
  10.

## Also landed

- **A vertical can look up an organisation number at Bolagsverket.** The connector
  shipped with a connection and its probes only, so there was no way to ask it
  anything. It now has a dispatch: the vertical emits a lookup request, declares
  where the answer lands, and the control plane looks the number up with the
  tenant's connection and invokes the bound operation **as the connection**, with
  found, not-found, invalid (refused locally, never sent) or refused. It lands from
  the dispatch rather than a sweep, so the answer arrives with the router's drain
  kick instead of at the next 15-minute pass — and it waits for the landing grant
  before calling the provider, because a dispatch in the gap between bind and
  grant hit a 403 that is terminal in the drain. Separately, the same connector is
  the pilot for **running a connector as its own script** rather than inside the
  control plane, behind a flag that is unset in every environment.
- **Microsoft 365 sign-in is one explicit choice** — client secret (the default
  and quickest), a platform-generated certificate (the most secure), or your own
  RSA pair whose certificate your admin already uploaded, parsed with Web Crypto
  and refused in the connector's own words when it is encrypted, not RSA, under
  2048 bits, not the certificate's, or expired. The platform never rotates a
  supplied certificate; a client secret takes an optional end date and is warned
  about from 30 days before it.
- **A Fortnox consent short of its scopes reads as needs-re-consent**, not a
  refused credential: the probe reports the shortfall, the sweep fails only the
  bindings that need a missing scope with a readable reason and no 403, and the
  connection view offers a Re-consent button.
- **`<sub-kanban>` takes column colours, `sortable="false"` and localisable
  labels** for every visible and announced word, resolved as the board's own
  labels, then the component library's translation registry for its language, then
  English — held by a test that replaces every label with a placeholder, drives
  each state a keyboard reaches, and refuses any English left in the text, the
  aria attributes or the announcements.
- **A password can be made to wait for a verified address.** A new setting on the
  auth server, off by default: sign-up sets no session, the verification link does,
  and an unverified sign-in with the right password is refused and sent a fresh
  link. The hard part was the trip *back*: the link now carries the relying party's
  original authorize request, re-issued without what the click has already
  answered, so clicking it verifies, signs in and lands on the app rather than on a
  sign-up page. An install can also now ask the platform for its own social-sign-in
  client instead of needing a staff run.
- **An RFC for an outside answer that decides a commit.** A cash-register engine
  needs a control code from a tax unit *inside* the transaction it is recording.
  The RFC weighs an in-transaction port, a host-staged port, reserve-then-record
  and connector dispatch against the regulation's own text, and recommends
  reserve-then-record with **no new kernel verb**: the in-transaction call rolls
  back the journal row of a request that already left, which is the record the
  regulation requires. The request is handed out once, with a send token, so a
  replay or a retry gets the attempt's state rather than permission to send again;
  the driver's send is fenced by the attempt's own deadlines. Proposed, no code.
  Alongside it, a vertical connector's answer now writes its state **fenced on the
  scope lease atomically** — the fence check and every write in one transaction on
  both hosts — replacing a non-atomic re-read.
- **The book's third edition**, reviewing weeks 42–46, with two new chapters: apps
  made of other apps, and screens. Eleven claims the review found overstated were
  corrected rather than softened.
- **A refused promote points at the approvals pane**, and the plugin checks for one
  at session start in a vertical, so a promote that CI left waiting on a person
  shows up above the prompt instead of after the next failed command.
- **Tests and CI:** the egress suite caches the Python runtime bundle and boots it
  in `beforeAll`, where a 17 MB download inside whichever test asked first was a 60
  second timeout; a Stripe test waits for the held call rather than a tick; the
  store canary fixture holds 300 rows, enough for a graph repository; the Substrat
  plugin's hooks tests and a strict validate run on every `plugin/` change; and
  `ci-scope` and the preview filter read changed paths NUL-delimited, so a quoted
  path is read as the tree spells it.
- **Docs:** a Bolagsverket connector page, with drift coverage extended to the
  private connectors the index lists.
